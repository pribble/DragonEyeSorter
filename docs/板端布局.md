# 板端布局

板上**有哪些文件、谁放的、放在哪、什么规矩**。回答四类问题：这套东西由哪几份文件组成、每一份从哪来、丢了会怎样、怎么核对板上那份是不是当前版本。

配套的两份文件（分工不重复）：

| 文件 | 给谁看 | 内容 |
|---|---|---|
| [scripts/deploy/manifest.tsv](../scripts/deploy/manifest.tsv) | 脚本 | **机器读的清单**：源 → 板端路径 → 类别（决定权限）→ 改完要不要重启服务 |
| 本文 | 人 | 结构、边界、引用规矩、上板前的要求 |

板上**只有 `des.env` 一个文件里有路径**，其余脚本与程序都从它取 —— 所以"文件该怎么放"这条规矩的落点是 `des.env`，不是散在各处的 `scp` 命令（见 [scripts/deploy/out/des.env](../scripts/deploy/out/des.env)）。

## 1. 两个分区

| 分区 | 文件系统 | 挂载点 | 放什么 | 谁改 |
|---|---|---|---|---|
| p1（252MB） | FAT32 | `/mnt/mmcblk0p1` | 启动件：`BOOT.bin`（= FSBL + 比特流 + U-Boot）、`boot.scr`、`system.dtb`、`uImage.lz4`、`initramfs_backup/` | [scripts/README](../scripts/README.md) 的 bootbin 一节打包后手工换，**不归部署器管** |
| p2（3.6GB，余约 2.9G） | ext4 | `/`（`root=/dev/mmcblk0p2`，另被 automount 再挂一次到 `/mnt/mmcblk0p2`） | 根文件系统 + 我们全部的文件 | 应用件走 [scripts/deploy](../scripts/deploy/README.md) |

```
/                                   ← p2 ext4（持久化根分区）
├── etc/init.d/S90des               →(软链) /root/des/des_service.sh
├── opt/                            厂家件，我们不传也不动
│   ├── armnn_lib/                  ArmNN 32.1（含 Alnpu 后端、libfmt.a）
│   ├── ffmpeg_opencv4.7.0_aarch64/ OpenCV 4.7 + FFmpeg
│   ├── bin/                        cma_mem.ko / hard_npu.ko / soft_npu.ko / jpu.ko / mipicam.ko …
│   ├── inputs/  scripts/           厂家 demo 的网络描述与启动脚本
├── usr/share/fonts/wqy-zenhei/     UI 中文（wqy-zenhei.ttc）
├── root/
│   ├── des/                        ★ 产品运行时（下面第 3 节）
│   ├── bin/                        手动上板的测试 / 调试件（第 4 节）
│   └── des.bak-*/                  整目录改名备份，**不属布局**，收尾后删
└── mnt/mmcblk0p1/                  ← p1 FAT32 启动分区
    ├── BOOT.bin                    当前启动的比特流
    ├── BOOT.bin.prev               上一个**确认能用**的版本（换新版前先留）
    ├── BOOT.bin.vendor             厂家原版，**永远别动**
    ├── BOOT.bin.v5                 自留的历史版本
    ├── boot.cmd / boot.scr / system.dtb / uImage.lz4
    └── initramfs_backup/           厂家原启动方式（回退用）
```

启动链、`boot.scr` 的改法、换 `BOOT.bin` 的完整步骤见 [开发环境与构建](开发环境与构建.md)「启动链 / SD 卡布局」与 [环境与上手](环境与上手.md) §5；本节只登记**板上实际有哪些文件**。

## 2. 根分区上的四类文件（判据：谁负责更新）

| 类别 | 落点 | 谁更新 | 清单管不管 |
|---|---|---|---|
| **产品运行时** | `/root/des/` | [scripts/deploy](../scripts/deploy/README.md)：`deploy.ps1`（可 `-DryRun` 对比） | 管，10 条 |
| **手动上板件**（测试 / 调试 / 校准 / 回归） | `/root/bin/` + `/root/des/*.sh` 里那三个测试脚本 | 要用时自己 `scp`，用完可删 | **不管**（故意不登记，别往清单里加） |
| **板上生成件** | `/root/des/`：`autostart.conf`、`ui_params.json`、`calib.json`、`data/` | 板上自己写 | 不管，**别覆盖、也别搬回仓库** |
| **系统与厂家件** | `/opt/`、`/usr/share/fonts/`、`/etc/init.d/S90des`、`/mnt/mmcblk0p1/` | 装机时定，运行期不动 | 不管 |

## 3. `/root/des/`：产品运行时（清单 10 条）

```
/root/des/
├── des.env              路径唯一来源（先 source 它，其余文件才有路径）
├── des_app              主程序（ps/build/ 交叉编译产物，不入库）
├── des_app.json         主配置：相机 / 定位 / 跟踪 / 抓取 / 测量 / 机械臂 / 存储 / 配方
├── recipes.json         产品配方（换型；界面或 CAN RECIPE 切换）
├── label_list.json      类别表唯一源（训练 / NPU JSON / 分拣映射 / UI / 数据库同源）
├── part_cls.json        ┐ NPU 网络描述 + 量化模型：**两个必须同批导出、名字不能改**
├── part_cls_uint8.onnx  ┘
├── des_service.sh       守护进程：开机自启入口（/etc/init.d/S90des 指向它）、拉起 can_up + des_app、崩溃退避重启
├── can_up.sh            CAN 起接口（经典模式被控制器拒时自动退 FD）
├── des_app.sh           启动器：缺 /dev/mipicam 时先 insmod 再 exec des_app
├── autostart.conf       ← 板上生成（des_service.sh 首次运行写缺省）：ENABLED / MODE / CAN / CAN_MODE / ARGS
├── ui_params.json       ← 板上生成（界面改参数 / 换配方时才写）：**覆盖 des_app.json 的同名字段**
├── calib.json           ← 板上生成：相机 / 传送带 / 手眼标定（未标定时**不存在**，用 des_app.json 的占位值）
└── data/
    ├── service.log(.1)  服务事件（超 1MB 轮转成 .1）
    ├── des_service.pid  每份目录一个（`--dest` 装的测试目录不抢生产那个）
    ├── log/<日期>/parts_<会话>.csv + img/*.jpg   判定记录（40 列）与 NG / 复检裁切图
    └── collect/<会话>_<类名>/                     collect 采的训练图
```

各件缺了会怎样：

| 缺什么 | 现象 |
|---|---|
| `des_app` | 服务起不来，5 分钟内退出 5 次后放弃（`service.log` 有记录） |
| `des.env` | 脚本**直接报错退出**，不静默退化 |
| `des_app.json` | `des_app` 打不开配置（裸跑不带 `-c` 时是当前目录，见下节） |
| `part_cls.json` | **不报错停机**，只是关掉 NPU 分类：日志 `npu: cannot open …`，零件落成"未分类 / 复检" |
| `label_list.json` / `recipes.json` | 类别表 / 配方缺失，按代码缺省走（配方缺 = 只有配方 1） |
| `calib.json` | 正常：用 `des_app.json` 里的未标定占位值，日志提示 `no calib.json, camera mapping is the uncalibrated placeholder` |

`part_cls.*` 由 `train/export_npu.py` 导出（`models/` 里没有就是没导出，本地编不出来），两个文件**必须同一批**，`part_cls.json` 里的 `model` 字段指向那个 `.onnx`。

**两个"板上生成"的配置不是第二配置源**：`autostart.conf` 只决定服务怎么起；`ui_params.json` 是**覆盖层** —— 它存在时，界面上的带速 / 尺寸公差 / 最小置信度 / 存档图片 / 配方号会盖掉 `des_app.json` 的同名字段（`pl_mode` / `pl_thr` 是 des_vision 显示设置，`des_app.json` 里没有对应键）。所以**想让某个值成为默认就改 `ps/src/des_app.json`**，别让实测 / 定稿值只活在板上这份（历史教训：[log/2026-10-16-部署器上板验证](log/2026-10-16-部署器上板验证.md) 的皮带实测值）；删掉 `ui_params.json` 即回到 `des_app.json` 的值。

## 4. `/root/bin/`：手动上板件

只有"要用才传、用完可删"的东西，**不进清单**，所以部署器不跟踪它们是哪一版：

- 调试 / 陪测：`desreg`（寄存器 / 舵机总线 / 步进；`des_app` 在跑时只读 `r`）、`canplc`（扮「产线 PLC」）
- 测试程序：`test_scheduler`、`test_calib`、`test_measure`、`test_belt_hil`、`test_can`、`test_npu`
- 测试脚本（落 `/root/des/`）：`pl_check.sh`（换比特流回归）、`soak.sh`（长跑）、`display_check.sh`（HDMI 黑屏对照）

```bash
scp ps/build/desreg ps/build/canplc ps/build/test_* $BOARD_HOST:/root/bin/
scp scripts/deploy/out/pl_check.sh scripts/deploy/out/soak.sh scripts/deploy/out/display_check.sh $BOARD_HOST:/root/des/
```

同目录里若出现 `desreg.v1`、`*.prev`、`live.png` 之类，是历次调试残留，不算布局；确认没用就删，别让它冒充"板上跑的那一份"。

## 5. 路径从哪来、相对引用怎么解析

- **脚本**：`SELF=$(readlink -f -- "$0")` → `DES_HOME=$(dirname SELF)` → `. "$DES_HOME/des.env"`。`readlink -f` 保证经 `/etc/init.d/S90des` **软链**调用时也认得自己在 `/root/des/`；`DES_HOME` 由脚本自己算、不吃继承值；`des.env` 缺失直接报错。
- **`des_app`**：不读这个文件，读 source 后 **export 的环境变量** —— `-c` 缺省 = `$DES_CONFIG`（没设就是**当前目录**的 `des_app.json`），`collect` 落盘 = `$DES_COLLECT`（`--out` 优先）。
- **配置里的相对引用**全部按 **`des_app.json` 所在目录**解析：`label_list`、`recipes_file`、`calib_file`、`npu.model`、`storage.dir`、`ui_params.json`。代码缺省值：`npu.model = part_cls.json`、`calib_file = calib.json`、`storage.dir = data/log`（→ 生产是 `/root/des/data/log`）。
- **跨目录的绝对值**只在 `des.env` 登记一处：`DES_TOOLS=/root/bin`、`DES_MIPICAM_KO=/opt/bin/mipicam.ko`。

于是**整套目录是自洽的**：`deploy.ps1 -Dest /root/des/test` 把整份另装到别处，它跑自己的程序、自己的配置、自己的日志与 PID 文件，生产那份一个字节不动（这也是"先在板上试新版"的推荐姿势）。

## 6. 上板前对文件本身的要求

| 项 | 要求 | 违反的后果 |
|---|---|---|
| 行尾 | `*.sh` / `*.env` 必须 **LF**（`.gitattributes` 已钉 `eol=lf`） | 板上执行报 `not found`（CR 被当成命令的一部分） |
| 行尾 | `*.json` 带 CR 无妨（CR 是合法空白，`nlohmann` 照解） | 只是 `md5sum` 直接比会误报"不同"，比对前先 `tr -d '\r'` |
| 权限 | 清单第 3 列决定：`script` / `bin` → `700`，其余 → `600` | 该能执行的跑不起来；或运行数据被误当可写配置 |
| 覆盖 | `des_app` 正在跑时覆盖会 `Text file busy`；覆盖运行中的 `des_service.sh` 会被拦下 | 传到一半失败、或新旧 PID 文件位置混用 |
| 启动 | 一律走 `./des_app.sh`（它会 insmod 驱动、带 `-c`、拒绝与自启服务抢硬件） | 裸跑 `./des_app` 读的是**当前目录**的配置，容易新程序 + 生产判据 |

改完要生效：`des_app` / `des_app.json` 等被 `des_app` 读的文件 → `des_service.sh restart`；脚本（`can_up.sh` / `des_app.sh`）下次启动才生效。

## 7. 怎么核对（不靠记忆，也不靠 `ls` 猜）

```bash
# PC 侧：只读对比「板上 vs 仓库/本地」，逐条报 需要更新 / 板上还没有 / 一致 / 本地缺产物
.\scripts\deploy\deploy.ps1 -DryRun
```

```bash
# 板上自查
ls -l /root/des                                        # 清单件在不在
md5sum /root/des/des_app /root/des/*.sh                # 与仓库对比（文本先 tr -d '\r'）
/root/des/des_service.sh status                         # 在不在跑 + 最近几条服务事件
cat /root/des/autostart.conf                            # 自启行为（ENABLED/MODE/CAN/ARGS）
ls -l /etc/init.d/S90des                                # → /root/des/des_service.sh
```

`des_app` 是**编译产物**：`--dry-run` 报"需要更新"通常只说明板端不是当前源码的构建，动手前先确认板上那份的来源（历史教训见 [log/2026-10-16-部署器上板验证](log/2026-10-16-部署器上板验证.md)）。`desreg` / `test_*` / 三个测试脚本**不在清单里**，部署器不跟踪它们是哪一版 —— 要用就先重传本机构建，别假设板上那份是当前源码的产物。

## 8. 边界

- 板端脚本与 `des.env` 的唯一源是 `scripts/deploy/out/`（就地改、就地提交，2026-10-16 由 `ps/board/` 迁入），配置的唯一源是 `ps/src/` 与 `models/`；`scripts/deploy/manifest.tsv` 只登记"哪份上到哪"，**不放副本**。
- 部署器**不编译、不反向拉取、不动系统件**：产物来自 `ps/build/`（`make -C ps all`）；板上手改的文件不会自己回仓库，要改就改 `scripts/deploy/out/` 再部署。
- 不入库的是**能由源码编出来的二进制**：`ps/build/`、`scripts/deploy/out/des_app`；反过来，`out/` 里的**脚本、`des.env` 与配置入库**——它们就是"这一版发到板子上的是什么"的凭据，脚本与 `des.env` 更是唯一源。模型权重（`*.onnx`）同样不入库（[AGENTS.md](../AGENTS.md) 硬性约定第 7 条）。
- 板上实测的数字、哈希、目录快照写在 `docs/log/`，本文只写结构与规矩。
