# 板端布局

板上**有哪些文件、谁放的、放在哪、什么规矩**：这套东西由哪几份文件组成、每份从哪来、丢了会怎样、怎么核对。

**机器读的清单**是 [scripts/deploy/manifest.tsv](../scripts/deploy/manifest.tsv)（源 → 板端路径 → 类别 → 改完要不要重启服务），**清单条数与各目录文件数一律以它为准**；本文写给人看：结构、边界、引用规矩、上板前的要求。板上**只有 `des.env` 一个文件里有路径**，其余都从它取（见 [scripts/deploy/out/des.env](../scripts/deploy/out/des.env)）。

## 1. 两个分区

| 分区 | 文件系统 | 挂载点 | 放什么 | 谁改 |
|---|---|---|---|---|
| p1（252MB） | FAT32 | `/mnt/mmcblk0p1` | 启动件：`BOOT.bin`（= FSBL + 比特流 + U-Boot）、`boot.scr`、`system.dtb`、`uImage.lz4`、`initramfs_backup/` | [scripts/README](../scripts/README.md) 的 bootbin 一节打包后手工换，**不归部署器管** |
| p2（3.6GB，余约 2.9G） | ext4 | `/`（`root=/dev/mmcblk0p2`，另被 automount 再挂一次到 `/mnt/mmcblk0p2`） | 根文件系统 + 我们全部的文件 | 应用件走 [scripts/deploy](../scripts/deploy/README.md) |

```
/                                   ← p2 ext4（持久化根分区）
├── etc/init.d/S90des               →(软链) /root/des/des_service.sh
├── opt/ · usr/share/fonts/         厂家件（ArmNN、OpenCV、.ko、demo）与 UI 中文字体
├── root/des/                       ★ 产品运行时（第 3 节）
├── root/bin/                       手动上板件（第 2 节末）
└── mnt/mmcblk0p1/                  ← p1 FAT32：BOOT.bin、.prev（上一个确认能用的版本）、
                                   .vendor（厂家原版）、boot.scr、system.dtb、uImage.lz4、
                                   initramfs_backup/（回退用）
```

启动链、`boot.scr` 改法、换 `BOOT.bin` 的完整步骤见 [开发环境与构建](开发环境与构建.md)「启动链与 `BOOT.bin`」「SD 卡布局与烧卡」「部署与运行」；本节只登记板上实际有哪些文件。

## 2. 根分区上的四类文件（判据：谁负责更新）

| 类别 | 落点 | 谁更新 | 清单管不管 |
|---|---|---|---|
| **产品运行时** | `/root/des/` | [scripts/deploy](../scripts/deploy/README.md)：`deploy.ps1`（可 `-DryRun`） | 管，条数以 [manifest.tsv](../scripts/deploy/manifest.tsv) 为准 |
| **手动上板件**（测试 / 调试 / 校准 / 回归） | `/root/bin/` + `/root/des/*.sh` 里的测试脚本 | 要用时自己 `scp`，用完可删 | **不管**（故意不登记） |
| **板上生成件** | `/root/des/`：`autostart.conf`、`ui_params.json`、`calib.json`、`arm_home.json`、`data/` | 板上自己写 | 不管，**别覆盖、也别搬回仓库** |
| **系统与厂家件** | `/opt/`、`/usr/share/fonts/`、`/etc/init.d/S90des`、`/mnt/mmcblk0p1/` | 装机时定，运行期不动 | 不管 |
手动上板件的传法（不进清单、部署器不跟踪版本）：`scp ps/build/desreg ps/build/canplc ps/build/des_tool ps/build/test_* $BOARD_HOST:/root/bin/`；测试脚本 `scp scripts/deploy/out/pl_check.sh scripts/deploy/out/soak.sh scripts/deploy/out/display_check.sh scripts/deploy/out/des_tool.sh $BOARD_HOST:/root/des/`。四层产物见 [ps/README](../ps/README.md)。

## 3. `/root/des/`：产品运行时

```
/root/des/
├── des.env              路径唯一来源（先 source 它，其余文件才有路径）
├── des_app              主程序（run / live），ps/build/ 交叉编译产物，不入库
├── des_app.json / recipes.json / label_list.json   主配置 / 产品配方 / 类别表唯一源
├── part_cls.json + part_cls_uint8.onnx             NPU 网络描述 + 量化模型：必须同批导出
├── des_service.sh / can_up.sh / des_app.sh / shutdown.sh   自启链、CAN、启动器、关机
├── autostart.conf / ui_params.json / calib.json    板上生成（服务开关 / 界面覆盖层 / 标定）
└── data/                service.log(.1)、des_service.pid；log/<日期>/parts_<会话>.csv +
                         img/*.jpg（判定记录、NG / 复检裁切图）；collect/<会话>_<类名>/
```

各件缺了会怎样：缺 `des_app` 服务 5 分钟内退出 5 次后放弃；缺 `des.env` 脚本直接报错退出；缺 `des_app.json` 打不开配置；缺 `part_cls.json` 不报错停机、只关 NPU 分类（日志 `npu: cannot open …`，零件落成"未分类 / 复检"）；缺 `label_list.json` / `recipes.json` / `calib.json` 按代码缺省走（配方缺 = 只有配方 1；标定缺 = 用未标定占位值，日志 `no calib.json …`）。

`part_cls.*` 由 `train/export_npu.py` 导出（`models/` 里没有就是没导出），两个文件**必须同一批**，`part_cls.json` 的 `model` 字段指向那个 `.onnx`。`autostart.conf` 只决定服务怎么起；`ui_params.json` 是 `des_app.json` 的**覆盖层**（界面上的带速 / 尺寸公差 / 最小置信度 / 存档图片 / 配方号）。**想让某个值成为默认就改 `ps/src/des_app.json`**；删掉 `ui_params.json` 即回到 `des_app.json`（[log/2026-10-16-部署器上板验证](log/2026-10-16-部署器上板验证.md)）。

## 4. 路径从哪来、相对引用怎么解析

- **脚本**：`SELF=$(readlink -f -- "$0")` → `DES_HOME=$(dirname SELF)` → `. "$DES_HOME/des.env"`。`readlink -f` 保证经 `/etc/init.d/S90des` **软链**调用时也认得自己在 `/root/des/`；`DES_HOME` 不吃继承值；`des.env` 缺失直接报错。
- **`des_app` / `des_tool`**：读 source 后 **export 的环境变量**——`-c` 缺省 = `$DES_CONFIG`（没设就是**当前目录**的 `des_app.json`），`collect` 落盘 = `$DES_COLLECT`（`--out` 优先）。
- **配置里的相对引用**全部按 **`des_app.json` 所在目录**解析：`label_list`、`recipes_file`、`calib_file`、`npu.model`、`storage.dir`、`ui_params.json`；代码缺省 `npu.model = part_cls.json`、`calib_file = calib.json`、`storage.dir = data/log`。跨目录绝对值只在 `des.env` 登记一处：`DES_TOOLS=/root/bin`、`DES_MIPICAM_KO=/opt/bin/mipicam.ko`。

于是**整套目录是自洽的**：`deploy.ps1 -Dest /root/des/test` 整份另装到别处，跑自己的程序、配置、日志与 PID 文件，生产那份一个字节不动。

## 5. 上板前对文件本身的要求

| 项 | 要求 | 违反的后果 |
|---|---|---|
| 行尾 | `*.sh` / `*.env` 必须 **LF**（`.gitattributes` 已钉 `eol=lf`） | 板上执行报 `not found`（CR 被当成命令的一部分） |
| 行尾 | `*.json` 带 CR 无妨（CR 是合法空白） | `md5sum` 直接比会误报"不同"，比对前先 `tr -d '\r'` |
| 权限 | 清单第 3 列决定：`script` / `bin` → `700`，其余 → `600` | 该能执行的跑不起来；或运行数据被误当可写配置 |
| 覆盖 | `des_app` 正在跑时覆盖会 `Text file busy`；覆盖运行中的 `des_service.sh` 会被拦下 | 传到一半失败、或新旧 PID 文件位置混用 |
| 启动 | 一律走 `./des_app.sh`（`run` / `live`）或 `./des_tool.sh`：都会 insmod 驱动、带 `-c`、拒绝与自启服务抢硬件 | 裸跑 `./des_app` 读的是**当前目录**的配置，容易新程序 + 生产判据 |

改完要生效：`des_app` / `des_app.json` 等被 `des_app` 读的文件 → `des_service.sh restart`；脚本（`can_up.sh` / `des_app.sh` / `des_tool.sh`）下次启动才生效。

## 6. 怎么核对

```bash
# PC 侧：只读对比「板上 vs 仓库/本地」，逐条报 需要更新 / 板上还没有 / 一致 / 本地缺产物
.\scripts\deploy\deploy.ps1 -DryRun

# 板上自查
ls -l /root/des                                        # 清单件在不在
md5sum /root/des/des_app /root/des/*.sh                # 与仓库对比（文本先 tr -d '\r'）
/root/des/des_service.sh status                         # 在不在跑 + 最近几条服务事件
cat /root/des/autostart.conf                            # 自启行为（ENABLED/MODE/CAN/ARGS）
ls -l /etc/init.d/S90des                                # → /root/des/des_service.sh
```

`des_app` 是**编译产物**：`-DryRun` 报"需要更新"通常只说明板端不是当前源码的构建。`desreg` / `des_tool` / `test_*` / 那几个测试脚本**不在清单里**，要用就先重传本机构建（[log/2026-10-16-部署器上板验证](log/2026-10-16-部署器上板验证.md)）。同目录的 `desreg.v1`、`*.prev`、`live.png` 之类是调试残留，不算布局；核对以 [manifest.tsv](../scripts/deploy/manifest.tsv) 与本节命令为准。

## 7. 边界

- 板端脚本、`des.env` 与类别表 `label_list.json` 的唯一源是 `scripts/deploy/out/`（就地改、就地提交），其余配置的唯一源是 `ps/src/`；NPU 模型导出物在 `models/`（导出时生成、不入库）。`manifest.tsv` 只登记"哪份上到哪"，**不放副本**。部署器**不编译、不反向拉取、不动系统件**。
- 不入库的是**能由源码编出来的二进制**（`ps/build/`、`scripts/deploy/out/des_app`）；`out/` 里的**脚本、`des.env` 与配置入库**，就是"这一版发到板子上的是什么"的凭据；模型权重（`*.onnx`）不入库（[AGENTS.md](../AGENTS.md)「红线」· 入库边界）。板上实测数字、哈希、目录快照写 `docs/log/`。
