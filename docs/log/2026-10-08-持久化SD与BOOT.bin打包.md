## 二、持久化 SD 卡（✅ 上板通过）

做法：照官方 Ubuntu demo 的分区与 `boot.scr` 写法，根文件系统用 NPU demo 自己的（从 `uInitrd.lz4` 解出），内核 / 比特流 / 设备树原样。

| 验证 | 结果 |
|---|---|
| `mount \| grep " / "` | `/dev/root on / type ext4 (rw,relatime)` |
| `/root/keep_test` 重启后 | 仍在 |
| `run_mipicam_fb.sh` | camera 26.7~27.2ms / npu 25.7~25.9ms / 26.5~29.4fps，与 initramfs 时一致 |
| `devtmpfs` 上限 | 393.7M → 429.9M（不再占 ~160MB 内存放根文件系统） |

帧率在运行几分钟后从 29.4 降到 26.5fps，增量全在 ARM 侧 `resize`（34 → 37.7ms），NPU 与 camera 不变 → 疑似 CPU 发热降频，⚠ 待确认。

写卡踩坑：用 `mountvol X: /p` 卸载卷后写物理盘，写完头部分区表时 Windows 立刻重扫描，报"设备未就绪"。改为对每个卷 `FSCTL_LOCK_VOLUME` + `FSCTL_DISMOUNT_VOLUME` 并保持句柄、分区表最后写，一次成功（4GB / 257s，读回 MD5 一致）。

## 五、BOOT.bin 重打包（✅ 2026-10-09 上板通过）

上板结果：卡上 `BOOT.bin` 换成 `41489e57…` 后重启，FSBL → `PL init done` → U-Boot → 内核 → ext4 根分区 → 登录全部正常；`run_mipicam_fb.sh` 每 10s 282 / 271 帧（≈28fps），与原版一致。启动日志中 `pca954x probe failed`、`vdmafb Failed to request vdma channel`（随后延迟加载成功）在原版 BOOT.bin 下同样存在；`mounting devtmpfs on /dev failed: busy` 是持久化根分区下内核已自动挂载 `/dev`、`/init` 再挂一次所致，无害。

文件级对比：

厂家 `BOOT.bin`（`-read` 结果）：

| 分区 | 偏移 | 长度 | 载入 / 执行 | 属性 | 内容 |
|---|---|---|---|---|---|
| P0 | 0x3c0 | 0x30d40 | 0x61000000 / 0x61000000 | 0x820 | FSBL |
| P1 | 0x31100 | 0x3dd3c0 | 0x200000 / 0xffffffff | 0x8a0 | 比特流 |
| P2 | 0x40e4c0 | 0xe22c0（有效 0xe2248） | 0x200000 / 0x200000 | 0x820 | U-Boot |

配方见 [scripts/bootbin/boot.bif](../../scripts/bootbin/boot.bif)。结果：大小相同、分区头全同、FSBL / U-Boot 区逐字节相同；**仅比特流区末尾 32 字节**不同（原版 `0xff`，新版为比特流自带的 `0x80000000` 填充字）及对应校验值 → 新旧 BootGen 对比特流尾部处理不同。同输入重复打包 MD5 稳定为 `41489E57…`。

调试中的坑：
- 截取 U-Boot 要用 `unencrypted_length`（0xe2248），`total_length` 含 64 字节 SHA2 校验值。
- `objcopy --rename-section` 必须带 `contents` 标志，否则段内容为全 0，BootGen 照样"成功"。
- U-Boot 用裸 `.bin` 入包时执行地址为 0xffffffff；包成带入口 0x200000 的 ELF 后才对。
- `soc_sdk/soc_base/platform/soc_prj.bit` 与 `soc_prj_Runs/*/soc_prj.bit` MD5 不同，但打出的 BOOT.bin 一样（差异在 `.bit` 文件头）。
