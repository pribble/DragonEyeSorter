# 2026-10-23 CAN 双节点实测（PC USB-CAN ↔ 板）

**接线**：J11 插头（KF2EDGK 3.81mm 6 位）：3 CANH → 适配器 H、2 CANL → L、1 GND → GND；终端只有板上 R120（适配器端未加，台面短线）。适配器 ZQWL-UCAN-101E（COM9，固件 V2.7）插笔记本。板上 PL v12，`des_app run --can can0`（自启服务，空闲，无 `--go`）。

## 过程

1. `python zqwl.py`：读出 UCAN-101E / V2.7。打开前板上 `can0` 为 ERROR-PASSIVE（开机后 215 帧都没人应答）——正常，适配器不开通道就不应答。
2. `python zqwl.py listen -s 8`：收到板子 STATUS `0x181`（约 10 帧/s，心跳序号连续）与 COUNTS `0x182`（1 帧/s）；适配器 TEC / REC 0。板子回落到 ERROR-WARNING（帧开始被应答，发送错误计数下降）。
3. `python zqwl.py send …`（只发不会让设备动的命令）：
   - `100#0207` 停止（本来就停着）→ ACK `00 07 00`（接受）
   - `101#F40109` 带速 50.0mm/s（与当前相同，皮带不转）→ ACK `01 09 00`
   - `100#0911` 不存在的命令 9 → ACK `00 11 03`（未知命令，正确拒绝）
4. 2 分钟链路测试 `pc/plc_sim/can_soak.py`（新增）：PC 心跳 2Hz + 每 0.5s 轮流「停止 / 带速 50」，**从不发启动**；统计应答往返（PC 时钟）、STATUS 间隔与按板子心跳序号算丢帧。

## 发现并修复：应答与排队帧背靠背 → 丢帧

| | 命令 / 应答 | 应答往返（中位 / p95 / 最大） | STATUS 收 / 丢 |
|---|---|---|---|
| 修复前（120s） | 240 / 240，0 未应答 | 44.0 / 61.4 / 76.8ms | 1033 / **34**（间隔 >150ms 35 次） |
| 只发心跳、不发命令（60s） | — | — | 530 / **0** |
| 修复后（120s） | 240 / 240，0 未应答 | 44.5 / 61.4 / 77.0ms | 1063 / **0** |

原因：`Runner` 收到命令后应答用 `can_send` 立即发，同一周期末尾 `flush_tx()` 再发一帧排队的 STATUS → 两帧背靠背写进控制器，丢一帧（与 10-11 回环浸泡里「PART 突发时丢 STATUS」同一现象；驱动 / 控制器不报错，板上接口 TX errors 不涨）。改法（`ps/src/app/runner.cpp`）：应答进单独的 `ackq_`，`flush_tx()` 先发它、再发 `txq_`，**每周期仍只发 1 帧**；命令在周期开头处理、应答在同一周期末尾发出，往返时间不变。

应答往返 44ms 的大头是 PC 一侧：USB 虚拟串口收发 + Python 线程；板子内部处理 ≤ 1 个周期（60Hz，≤16.7ms）。板上回环的协议往返是 359µs（10-20）。
